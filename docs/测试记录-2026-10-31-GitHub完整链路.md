# GitHub 真实模型、私有仓库、CI 与 Hook 验收（2026-10-31）

## 环境及边界

使用用户已有的 DianStar 专用 GitHub 登录、当前 `deepseek-flash` 模型及已安装的官方 GitHub MCP 服务。模型与 GitHub 返回未模拟；实际工具调用经过 `run_turn`、`ToolGateway`、本地 Git stdio 服务和官方 GitHub MCP。每个模型任务仍受原有 16 轮上限约束。

新建两个仅含示例内容的独立测试仓库：

- [公开测试仓库](https://github.com/wnagling/dianstar-acceptance-public-20261031-686819)
- [私有测试仓库](https://github.com/wnagling/dianstar-acceptance-private-20261031-686819)

准备阶段由验收控制程序创建仓库、安装最小工作流、克隆、设置测试副本作者及测试分支，再产生 `acceptance.txt` 改动。这些准备动作不计为 DianStar 模型自主完成的能力。工作流只运行固定 echo 与故意失败步骤，权限为 `contents: read`，没有 checkout、依赖安装或部署。

仓库范围只在验收进程中注入，凭据仍从原有登录读取；没有修改或复制用户的 `.env`、模型配置、MCP 配置或账号配置。确认界面使用真实 `DianStarApp` / `PermissionApproval` 的 80×24 Textual 测试驱动，校验目标后自动点击对应按钮，并记录次数。这是自动化界面验收，区别于人工在桌面终端点击。

## 本轮实现 GitHub 内容 Hook

新增 `hooks/github.py` 和统一事件 `before_github_write`，接入官方 GitHub 七个写工具。完整 JSON 参数和原始多行/嵌套字符串分别扫描，复用共享敏感内容规则、资源限制和已知凭据指纹，并纳入当前 GitHub 登录凭据。预览前检查、批准后执行前重查；拒绝和检查不完整会停止调用写工具。成功结果增加程序生成的 `content_check`，不改变官方输入字段或审批次数。

此 Hook 针对 PR、Issue、评论、审查等已接入写工具的待发送内容，不代表所有 GitHub API 都已开放，不代替私有访问、仓库范围、状态重查和审批，也不保证识别所有未知机密或语义外传。

在公开测试仓库的专用 [Hook Issue #2](https://github.com/wnagling/dianstar-acceptance-public-20261031-686819/issues/2) 中，通过真实 MCP、网关和 GitHub API 验证：

1. 正常创建 Issue，内容检查完成。
2. 注入确定性拒绝规则后，评论在预览阶段被拦截，未调用写工具。
3. 用户选择取消，未调用写工具。
4. 预览后、审批回调中改变检查规则，执行前重查拦截，未调用写工具。
5. 注入异常回调，得到检查不完整，未调用写工具。
6. 移除验收附加规则后正常发送评论，结果报告检查完成。

对官方连接的真实调用计数和独立远程回读均确认：Issue 下仅存在 `DIANSTAR_HOOK_ALLOWED` 一条正常评论，拒绝、取消、异常标记均未发布。验收附加规则只存在于测试进程，不写入用户配置，不能替换内置规则。上述 Hook 探针由固定范围的验收程序驱动，区别于上面的真实模型任务。

## 私有范围及跨 fork 限制

对本轮私有测试仓库，在同一有效账号下去掉应用私有访问范围，实际请求被拒绝为未确认公开仓库，未读取其内容。这证明 Token 有权访问不等于应用自动允许私有访问。

账号没有关联组织，用户确认没有第二个可控账号/组织。使用已有真实 fork `wnagling/tinyhttpd` 与公开上游 `cbsheng/tinyhttpd`，只运行 compare 与 PR 预览的读取逻辑；base/head 均为 `247de7e5dc47d59b79df90dc73938ae791ba1a15`。没有提交新差异，没有向该上游创建 PR 或发送消息。

因此，跨 fork 的实际差异创建及 PR 发布、第二个真实账号无权限等场景仍未验收，不能把这次只读预检计为完整通过。真实跨 fork compare 分页及冲突场景也未新增验收。
