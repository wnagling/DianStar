# 文件恢复与并发验收

本轮在首批 read/glob/grep/edit/write 的基础上，补齐统一跨进程锁、持久化恢复记录、批量失败补偿及历史撤销。既有改动和本机编辑器设置保留，没有提交、推送或重建可执行文件。

## 行为

每次 write、edit 和单文件删除都先记录修改前的实际工作区字节，而不是用 Git HEAD 代替。因此用户原来已有的未提交改动也属于恢复基线。成功结果包含 transaction_id，记录跨提问和进程保留，不依赖模型记忆。

新增工具：

| 工具 | 行为 |
| --- | --- |
| file_batch | 一份计划、一份完整差异、一次确认；关联的 edit/write/delete 最多 20 个不同路径，失败或执行中取消时尝试逆序补偿 |
| file_history | 按当前已接入项目查询本机记录编号、时间、文件和状态，只加载摘要，不读取或输出副本原文 |
| file_restore | 确认差异后撤销已完成记录，或继续中断的补偿；正常历史撤销生成新记录，可以继续撤销该恢复 |

已完成的修改发生逻辑错误时，可以选择对应编号撤销，但程序不能自动判断所有业务错误。测试失败也不自动选择恢复目标。有关系的多文件变更应使用 file_batch，独立的多次 write 不会被悄悄合并为整轮事务。

只读工具不因发现中断记录而修改项目，read 返回 recovery_pending。新的写入或命令预检可以先补偿此前中断的动作；也可以明确使用 file_restore 继续恢复。恢复遇到外部变化时保留现场，不能宣称已全部回滚；确认 keep_current 会保留当前文件并结束该记录，副本继续保留。

## 锁与执行边界

`security/file_locks.py` 使用 Windows LockFileEx；POSIX 分支使用 flock。文件读锁共享，写锁独占，多文件按规范路径排序；仓库与祖先目录锁协调命令、Git 应用计划和嵌套项目。文件锁不删除，避免删除后产生两个锁身份；进程退出由系统释放锁。正常等待有上限，繁忙或不能取得锁时不执行目标修改。

审批前的预检结束会释放锁，等待用户期间不持锁；执行时重新取得锁、核对版本。磁盘工作在线程执行，取消会通知执行线程并等待它补偿或保留恢复状态，避免请求已取消但后台仍悄悄继续修改。Git 写操作看到未解决的文件恢复会拒绝继续，通用命令也不能跳过恢复状态。

基础 edit/write/delete 的禁用也限制批量和恢复工具。只读后台策略阻止恢复写入；现有 Hook、参数、范围和审批检查继续有效。

## 持久记录与补偿

SQLite 使用 WAL 和 FULL 同步，先保存原始副本再碰目标。新内容写入同目录临时文件并刷新后，回读核对完整字节，将预期文件身份写入记录，再替换目标；删除也先记录原始字节。替换后和批次完成前再次核对版本。

补偿先检查整批当前状态，再逆序恢复。每次恢复也把预期恢复身份先写入记录，因此在原修改或恢复途中退出后，可以区分未应用、已应用和已恢复的步骤。日志写入失败、短写、文件冲突和恢复再次失败都有独立处理路径。提交完成后仅清理失败，不会因此反向撤销已经成功提交的文件任务。

状态包括 prepared、committed、rolling_back、rolled_back、conflict 和 preserved。recovery_required 表示仍需处理，不能当成恢复完成。连续历史撤销允许可信记录中的恢复版本链；外部重新写入相同字节也不会仅因内容相同而获准覆盖。

新建目录只在身份仍匹配且为空时清理；已有文件、外部新建文件、非空目录和变化过的恢复临时文件会保留。恢复副本的哈希、解密或记录范围检查失败时停止处理。

## 副本保护

Windows 默认保存在 `%LOCALAPPDATA%/DianStar/file-state`，恢复原文和独立摘要由当前账号的 DPAPI 加密，不放入项目。其他平台代码使用 0700 目录和 0600 文件，未声明加密，也未在本轮做非 Windows 实机验收。

测试通过可信环境变量 DIANSTAR_FILE_STATE_ROOT 指向 `.local` 内独立状态目录。副本不会成为模型消息、历史列表或审批原文；只显示脱敏差异及元数据。同目录暂存文件使用受保护的 `.dianstar-tmp-` 前缀，普通文件工具和 Git 内容检查不会将其当作普通项目文件发布。

恢复与锁的专门用例覆盖：

- 两个真实 Agent 子进程读取相同基线并同时申请修改，只有一个成功，另一个报告版本变化。
- 跨进程共享读锁、独占写锁、锁等待超时和子进程退出释放锁。
- 批量第二个文件失败，前一个恢复；取消发生在首次替换之后，等待补偿完成。
- 进程在替换之后退出、恢复进程再在恢复替换后退出，第三次继续恢复。
- 恢复再次失败后保留日志，之后继续；提交标记写入失败会补偿，已提交后的清理失败保留成功状态。
- 磁盘/日志写入失败、临时文件短写、损坏或无法解密的副本。
- 用户修改、确认期间修改、目录身份变化，以及内容相同但由用户重新创建的版本。
- 删除后恢复、撤销恢复、连续撤销、BOM/CRLF 字节保留、空目录清理。
- 只读读取不执行恢复，批量和恢复不能绕过基础工具禁用。

测试过程中修正了 SQLite 连接在用例清理前未关闭的问题；最后整组重新执行通过。历史查询改为小摘要，避免读取大量记录时把所有文件副本一起加载进内存。

最终检查还核对了批量仅本机配置的审批：无引号密码在详情中遮挡，主提示说明仅本机保存；删除确认明确说明会保存恢复记录。

真实模型使用当前 DianStar run_turn 和真实工具执行，在 `.local/file-recovery-live-20261101/project` 完成：读取 settings.py，用一个 file_batch 改配置并创建文档，查询 file_history，再 file_restore 整批撤销并回读核对。批量修改和恢复各批准一次。实际原始字节、BOM/CRLF 一致，新文档和新建空目录已移除，无暂存临时文件；原应用配置哈希核对一致，没有运行命令或 Git 修改。该验收使用固定范围自动审批回调，不表述成人工点击 UI。

## 仍然需要明确的限制

这套实现协调 DianStar 自己的进程，不强迫外部编辑器遵守锁；版本复查仍不能消除最后一次检查之后的所有系统调用竞争窗口。批量使用可恢复的补偿事务，不保证所有外部程序始终看不到中间状态。

恢复主要覆盖文件字节、基本权限位和已记录的新建目录，不是所有 ACL、所有者、扩展属性或原始时间戳的完整备份。当前工具不提供目录移动/递归删除事务，也不会自动撤销通用命令、Git 历史或远程副作用。

持续磁盘写满、损坏的存储、丢失的账号解密能力、数据库损坏或系统断电都可能阻止恢复。本轮真实进程退出测试不能替代断电与硬件故障测试；Windows 没有声明通用目录 fsync 保证。失败时停止、保留副本和现场并报告状态，不能承诺任何环境绝无故障。
