# 普通项目发布一次确认（2026-10-30）

本文记录当时的发布流程实现。后续已补上常规 Python 测试默认自动执行，测试命令的当前审批范围见 [常规测试验收](./测试记录-2026-10-30-常规测试自动执行.md)。

## 问题

原先每一批暂存、提交和推送分别申请确认，模型再逐文件调用时，会把一次发布变成多次弹窗。增加确认次数没有帮助用户理解最终目标，也不适合作为默认发布体验。

## 实现

- 新增 `tools/mcp/servers/git/publish.py` 和 `git_publish` MCP 工具。输入明确的文件列表、提交说明、远程名与目标分支，形成一次批准的计划。程序完成暂存、提交、普通推送和真实远程 SHA 核验，内部步骤不再分别请求批准。
- 私有索引预览最终内容，不更改用户暂存区或 HEAD；完整文件列表、变更统计、提交身份、项目、目标地址、将一并推送的已有本地提交和可选的上游关联可审阅。确认卡片显示紧凑摘要，详情保留全部文件，80 列下仍可操作按钮。
- 包含新增文件和明确删除的文件；对已有暂存但未选入计划的文件拒绝自动扩大范围。保留未选的工作区修改。不接受目录、通配符、强推或删除分支参数。
- 绑定文件字节、批准的树、暂存区、分支、身份和远程状态；确认后变化则停止。各阶段继续执行敏感内容 Hook；远程分叉时不自动整合。
- `ToolRegistration.required_tools` 是可信注册代码中的平面依赖。组合工具尊重底层 stage/commit/push 的禁用和明确禁止，确认期间撤销或替换底层工具也停止，不授予模型通用写权限。
- MCP 适配层保留执行错误中的 `completed_steps`、`commit`、`remote_verified` 和恢复说明。推送失败时保留已创建提交；不能把部分完成误报成什么也没执行，也不自动重复提交或推送。
- 修复索引错误的 `source=git_index` 在 MCP 准备阶段丢失的问题，使模型能根据实际错误来源处理，而非猜测差异引用。
- 系统提示引导发布前检查范围、必要新增依赖与项目验证，优先调用一次确认发布；已有提交单独推送仍使用 `git_push`。工具不自动运行测试命令，命令审批保持原机制。

- 后补 3 项通过（12.997 秒）：假模型经真实应用入口、Git stdio MCP 和本机 bare 远程完成一次确认发布；索引来源转发；80 文件的紧凑摘要、完整详情和单次确认按钮。
- 最后结果不确定处理 3 项通过（26.204 秒）：提交已成功但回执丢失时返回 `failed_step` 和 `outcome_unknown`，不能把缺少成功回执当作未执行；推送失败保留提交，真实远程拒绝后的信息仍可穿过 MCP 适配层。
- 最终预览与界面 2 项通过（10.940 秒）：作者、将一并推送的已有提交和可选分支关联在详情中可审阅，发布仍只确认一次，80 列界面可展开完整文件范围。
- 包括真实远程拒绝接收时的部分进度保留、取消/缺失审批/撤销不写入、确认后选中文件或远程变化、敏感路径与令牌拦截、未选暂存范围拒绝等。
