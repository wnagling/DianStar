## 产品定位

agentTry 是面向 PC 的通用 Agent。长期方向是具备强大的多 Agent 协同能力和高质量的记忆管理能力，首阶段聚焦工程开发场景。

### 自研核心与外部 Agent 并存

agentTry 保留并逐步完善自研 Agent 的基础能力，同时支持接入 Claude Code（CC）等外部 Agent。前期实际工作可以由 CC 作为主力，自研能力通过可运行、可验证的小任务逐步成长，服务于学习核心机制和形成自身特色的目标。

- **自研核心**：由 agentTry 管理用户目标、任务状态、记忆、上下文、验收和执行记录，逐步实现任务拆分与调度。
- **自研执行能力**：能够直接调用模型 API，亲手实现多轮交互、工具定义与参数验证、工具执行与结果回传，以及根据反馈继续执行的循环；逐步补充错误处理、超时、取消和任务恢复。
- **外部执行能力**：能够将任务委派给 CC 等外部 Agent，复用其工具执行及相关能力。自研 Agent 与外部 Agent 作为可选择的执行方式并存，按照任务需求和已验证的能力分配工作。
- **能力演进**：外部 Agent 的接入与自研能力建设共同推进；自研 Agent 应能独立完成范围明确的任务，不以调用外部 Agent 作为唯一执行途径。

### 任务交接与记忆归属

- 为自研 Agent 和外部 Agent 定义一致的任务与结果交接约定：输入包含目标、有效约束、相关事实及来源、工作范围和验收条件；输出包含完成状态、结果、改动、验证证据和未解决问题。
- 整体任务状态与长期记忆由 agentTry 管理。外部 Agent 的会话 ID 和执行历史作为执行记录关联到任务，其返回的信息经验证后再选择性沉淀为长期记忆。
- 外部 Agent 的上下文和记忆加载范围应明确配置；按需传递背景或提供检索能力，避免重复注入全部历史及相互冲突的记忆。
- 不同任务优先使用独立会话，同一子任务的连续执行可保留或恢复会话；切换执行者或新建会话时交接必要状态，避免丢失约束与有效进度。

### 阶段推进方向

先跑通自研 Agent 的最小模型与工具执行闭环，并接入 CC 完成实际任务，再根据任务表现逐步完善自研能力。以实际需求形成交接约定，初期不引入完整的插件框架。

候选起步验证是：自研 Agent 完成一个只读的项目分析任务，CC 完成一个范围明确的代码修改任务，两者采用一致的任务记录和结果格式。具体场景与验收标准仍待确定。

## 产品愿景

打造一个能够围绕用户目标，协调不同模型的多个 Agent、使用本机工具，并通过分层记忆和精细的上下文管理持续推进复杂任务的 PC 通用 Agent。

追求的不只是功能可用，还包括协作效果、执行可靠性、记忆准确性和上下文利用效率。以下内容描述长期愿景，不代表全部纳入首版。

### 多 Agent 与多模型协同

- 支持任务拆分、角色分工、依赖协调、信息交接、冲突处理，以及结果整合与验证。
- 支持使用不同模型承担不同任务，根据任务需求和模型特点组织协作。
- 支持子 Agent 并发执行同类或重复性任务，合理管理任务分配、并发规模、重试、取消和结果汇总，避免无意义的重复执行及工作冲突。
- 以实际任务质量和协作效率衡量能力，而不是单纯增加 Agent 数量；能够判断何时适合分工或并行，何时适合单 Agent 执行。

### 分层记忆与知识库

- **短期记忆**：维护当前任务目标、近期交互、执行状态与未解决问题，保证任务推进的连续性。
- **长期记忆**：沉淀稳定的用户偏好、项目约定、已确认决策和可复用经验，并做好更新、纠错与失效管理。
- **按需查阅的知识库**：组织文档、代码资料和历史产物等参考内容，在需要时检索，而不是将全部资料放入模型上下文。
- 做好短期与长期记忆之间的管理和转换：有选择地沉淀值得保留的信息，根据当前任务召回相关记忆，避免把未经确认的推断固化为事实。

### 上下文长度与对话筛查

- 严格关注每次发送给模型的上下文长度，根据不同模型的限制管理 token 预算，并为输出及后续交互预留空间。
- 具备对历史对话的筛查、压缩与裁剪能力，识别重复、过时、已被替代或与当前任务无关的内容。
- 裁剪时保护当前目标、有效约束、关键决策与未完成事项，不能只按时间先后机械删除旧对话。
- 将移出当前上下文与删除历史记录区分开，必要时能够查回原始信息，减少压缩造成的信息丢失。

## 实现愿景需要考虑的方面

以下内容作为后续产品设计与质量评估的依据；具体方案、优先级和首版范围仍待讨论。

| 方面 | 需要考虑的问题 | 对愿景的影响 |
| --- | --- | --- |
| 任务与验收 | 如何把用户目标变成可执行任务？什么证据能证明完成？ | 所有 Agent 围绕一致目标工作，避免局部完成但整体不符合需求 |
| 协作与调度 | 谁拆任务、分配模型和整合结果？如何处理依赖、阻塞和冲突？ | 决定多 Agent 是否真正提高效率 |
| 工具与执行环境 | 可以操作哪些文件、命令、浏览器和应用？并发工作如何隔离？ | 明确执行能力与边界，避免相互覆盖工作 |
| 记忆的可信度 | 信息来自哪里？是已确认事实，还是某个 Agent 的推断？ | 防止错误信息进入长期记忆后持续影响其他任务 |
| 中断与恢复 | 断网、模型报错或程序退出后能否继续？如何避免重复执行已完成操作？ | 保证长任务可以可靠推进 |
| 用户参与方式 | 用户如何观察、纠正、暂停和接管任务？哪些行为需要确认？ | 让用户在自主执行过程中仍能掌握方向 |
| 资源与成本 | 如何分配 token、调用费用、并发量、耗时和本机资源？ | 避免多 Agent 放大消耗或相互等待 |
| 评估与可观测性 | 如何记录决策、工具调用、记忆召回和结果？如何复现失败？ | 支持问题定位、方案比较与持续改进 |

### 共享记忆的规则与可信度

- 每个 Agent 需要独立的工作上下文，并能访问完成任务所需的项目共享信息。
- 明确共享记忆的写入权限、验证条件，以及冲突和版本更新规则。
- 区分用户确认的事实、工具验证的结果和 Agent 推断，保留信息来源及状态。
- 例如，实现 Agent 记录“接口已经完成”，测试 Agent 记录“接口测试失败”时，需要结合各自来源和验证状态处理，不能简单让一条记录覆盖另一条。

### 基于任务状态管理上下文

- 明确维护当前目标、有效约束、已确认决策与待办事项，使筛查和裁剪能够依据任务状态进行。
- 较早的用户约束可能仍然有效，近期大量工具输出也可能已经失去价值；信息取舍不能只依赖时间顺序。
- 评估压缩是否保留影响任务正确性的内容，避免摘要文字流畅但关键约束丢失。

### 并发执行与操作副作用

- 区分并行分析与并行修改：多个 Agent 分析不同文件，与同时修改同一代码库，需要不同的协调机制。
- 明确工作范围隔离、修改合并、公共依赖变化的处理方式，以及最终整体验证的责任归属。
- 对批量同类任务，区分失败后的必要重试与意外重复执行，避免重复写入或其他重复操作造成副作用。

### 评估与持续改进

- 设计能够暴露缺陷的场景，包括任务中途重启、已确认需求发生变化、记忆相互矛盾，以及多个子 Agent 修改相关模块。
- 观察系统能否恢复任务、更新认知、处理冲突并交付正确结果。
- 将多 Agent 方案与单 Agent 方案比较，记录任务质量、耗时和成本，检验额外协作复杂度是否带来实际收益。
- 记录跨模型交接、上下文压缩和记忆召回对有效约束与任务结果的影响，为后续改进提供证据。

### 候选综合验证场景

在一个已有项目中完成跨多个模块的功能开发；过程中用户修改一次需求、任务中断一次；系统恢复后能够沿用有效决策，协调实现与测试，并提供可验证的最终结果。

这个场景用于讨论如何同时检验协作与记忆能力，尚未确定为首版场景。后续需明确：

- 需求变化后，相关任务与记忆是否正确更新。
- 中断恢复后，是否保留有效进度并避免重复执行已完成操作。
- 多 Agent 的修改能否整合，最终结果是否通过整体验证。
- 相较单 Agent，任务质量、耗时和成本是否获得合理改善。

## 已确定事项

- 项目名称：agentTry。
- 从零编写 Agent，理解并实现其核心机制。
- 首阶段开发语言：Python；此前的 Rust 选型与调整原因见 [编程语言选型](./编程语言选型.md)。
- 保留并逐步完善自研 Agent 的独立执行能力，同时支持接入外部 Agent；前期实际工作可由 CC 作为主力。
- 整体任务状态与长期记忆由 agentTry 管理，自研 Agent 与外部 Agent 通过明确的任务与结果约定交接工作。
